## 1. 背景と目的

akasyx_crawler は指定フォルダを再帰探索してファイル情報（SHA-256 を含む）を SQLite に蓄積するが、
**元ファイルは読み取り専用**であり、重複を検出しても `duplicate_of_id` に参照を記録するだけで
ファイルの移動・削除は一切行わない（crawler 設計書 §10.2 / §14）。

本プロジェクト akasyx_duplicate_detector は、その探索結果を使って
**「保存用フォルダ」に内容重複のないファイル集合を構築する**ことを目的とする。

### 目的の要約

- あらかじめ **保存用フォルダ（アーカイブ）** を指定しておく
- **投入元**（追加したいファイル、またはフォルダ）を指定すると、
  akasyx_crawler を呼び出して探索し、ファイルハッシュ値を取得する
- 保存用フォルダの DB に **同一ハッシュが登録されていなければ**、
  そのファイルを保存用フォルダへ **移動** し、DB に登録する
- **ハッシュが重複したものは移動せず、投入元のフォルダにそのまま残す**
- 残った重複は記録しておき、後から `delete-duplicates` でまとめて削除できる
- 保存用フォルダは人が直接触ることもあるため、`verify` で DB と実体の
  整合性を検査し、ズレたものに**処置予定フラグ**を立てられる

### 設計の基本原則

| 原則 | 内容 |
|------|------|
| DB が正本 | 「保存フォルダに何が入っているか」の真実は `archive.db`。ファイル名・配置は人間可読性のためのもので、判定には使わない |
| 検証してから消す | 元ファイルを削除するのは、**移動先の実体とハッシュを検証した後**のみ。検証前に元を消す経路を1つも作らない |
| 判定不能は動かさない | ハッシュが取れなかったファイルは「新規」とみなさず、投入元に残す |
| crawler は無改造 | crawler は CLI として呼ぶだけ。crawler 側に detector 用の変更を入れない |

## 2. スコープ

### やること（v0.1.0）

| 項目 | 内容 |
|------|------|
| 取り込み（add） | 投入元を crawler で探索 → ハッシュ照合 → 新規のみ保存フォルダへ移動 → DB 登録 |
| 重複の据え置き | 内容が重複したファイルは移動せず投入元に残す。判定内容を DB に記録 |
| 重複の後始末 | `delete-duplicates` で、据え置いた重複を検証付きで削除（またはゴミ箱退避） |
| 整合性チェック | `verify` で保存フォルダを再スキャンし、missing / DB未登録 / ハッシュ不一致 / 移動 を検出 |
| 処置予定フラグ | verify の検出結果に `disposition`（quarantine 等）を立てる。実移動は将来対応 |
| クラッシュ復旧 | 移動の途中で落ちた場合に、次回起動時へ安全に引き継ぐ |
| ドライラン | `--dry-run` で、何が移動され何が残るかを実行せずに確認できる |
| CSV レポート | crawler と同じく `dist/log/` に判定結果を CSV 出力 |

### やらないこと（v0.1.0）

| 項目 | 理由 |
|------|------|
| 独自のファイル探索 | crawler の責務。detector は探索結果を消費する側に徹する |
| 独自のハッシュ計算（探索時） | 同上。ただし**移動後の検証**では detector 自身が再計算する（§7.3） |
| 類似判定（完全一致以外） | v0.1.0 は SHA-256 完全一致のみ。perceptual hash 等は将来拡張 |
| 隔離フォルダへの実移動 | フラグを立てるところまで。実移動は将来拡張（§16） |
| SharePoint 等リモートの取り込み | 実体を移動できないため。crawler v0.2.0 の対応後に検討 |
| 保存フォルダの自動仕分け | 年別・拡張子別の再配置は将来拡張 |

## 3. akasyx_crawler との関係

### 連携方式：CLI 呼び出し + DB 読み取り

crawler は `crawler/pyproject.toml` で `package = false`（モジュール直置きのフラット構成）を宣言しており、
`import collector` のようなトップレベル import に依存している。**ライブラリとして import する構成には向かない**ため、
detector は crawler を **サブプロセスとして実行し、出力された `file_inventory.db` を読み取り専用で参照する**。

```
detector ──subprocess──> crawler/main.py <投入元> --db-dir <detectorの作業領域>
         <──read only─── dist/db/file_inventory.db (fs_scans / fs_files)
```

### この方式を採る理由

- crawler 側に一切の変更が要らない（crawler の「元ファイルは読み取り専用」原則を壊さない）
- crawler が v0.2.0 で SharePointSource を追加しても、detector 側は `fs_files` を読むだけなので影響を受けない
- 境界が CLI と SQLite スキーマに固定されるため、テストで crawler をモックしやすい（§14）

### detector が参照する crawler の列

`fs_files` から次の列のみを読む。他の列（`metainfo` / 昇格列など）は v0.1.0 では使わない。

| 列 | 用途 |
|---|---|
| `path_abs` | 移動元の絶対パス |
| `path_rel` | 保存フォルダ内の配置を決めるための相対パス |
| `name` | ファイル名 |
| `size` | 0 バイト判定・ハッシュ照合の検算 |
| `filehash` / `hash_algo` | **重複判定の主キー**（同一 algo 同士でのみ照合 — crawler §10.2 の方針を踏襲） |
| `mime_type` | DB に転記（参考情報） |
| `modified_at` | DB に転記（由来情報） |
| `last_seen_scan_id` / `status` | 今回のスキャンで確認された `active` 行だけを対象にする |

### crawler の呼び出しパラメータ（既定）

| 引数 | 既定値 | 理由 |
|---|---|---|
| `--db-dir` | `<detector>/dist/db` | crawler の既定（crawler 自身の dist/）に書かせない |
| `--log-dir` | `<detector>/dist/log` | 同上 |
| `--gitignore-mode` | `off` | **重要**: crawler の既定は `nested` で、投入元に `.gitignore` があると意図せず除外される。取り込み対象を勝手に減らさない |
| `--no-meta` | 付与する | 形式別メタデータは重複判定に不要。任意依存（`--extra meta`）も不要になる。`--with-meta` で無効化できる |
| ハッシュ | 常に有効 | `--no-hash` / `--hash-max-size` は**渡さない**。ハッシュが無いと判定できない |

crawler はサブプロセスとして detector とは別の `.venv` で動くため、起動時に
`VIRTUAL_ENV` を環境から外す（detector の venv を持ち込むと uv が
「プロジェクトの環境と違う」と警告を出し、意図しない環境で走りかねない）。

`--full-scan` は付けない。同じ投入元を再度 add したとき、crawler の差分スキャンにより
未変更ファイルは `unchanged` として再ハッシュされないが、`fs_files` には行が残っているため
detector 側の判定には支障がない（§7.1 の「今回の scan_id で確認された active 行」を対象にする）。

### スキャン ID の特定

crawler は実行した scan_id を標準出力に返さないため、次の手順で特定する。

1. 実行前に crawler DB の `SELECT MAX(id) FROM fs_scans` を記録する（DB が無ければ 0）
2. crawler を実行する
3. 実行後に `SELECT * FROM fs_scans WHERE id > <前回max> ORDER BY id DESC LIMIT 1` を取る
4. その行の `status` が `completed` 以外（`interrupted` / `time_limit` / `failed`）なら、
   **取り込みを中止する**。走査が不完全な状態で移動を始めると、投入元の一部だけが移動して
   残りの判定が次回に持ち越され、利用者から見て挙動が不可解になるため

## 4. システムアーキテクチャ

```
                         ┌─────────────────────────────┐
    投入元フォルダ ─────> │ crawler_client.py           │
    （追加したいファイル） │  crawler をサブプロセス実行 │
                         └──────────┬──────────────────┘
                                    │ fs_files（読み取り専用）
                                    v
                         ┌─────────────────────────────┐
                         │ ingest.py — 判定             │
                         │  0バイト / ハッシュ無し /    │
                         │  既存ハッシュ / 新規         │
                         └──────────┬──────────────────┘
                        新規のみ     │        重複・スキップは投入元に残す
                                    v                    │
                         ┌─────────────────────────────┐ │
                         │ mover.py — 3フェーズ移動     │ │
                         │  pending → 移動 → 検証 →     │ │
                         │  stored                      │ │
                         └──────────┬──────────────────┘ │
                                    v                    v
                    ┌───────────────────────────────────────────┐
                    │ 保存用フォルダ                            │
                    │  <archive>/<投入元名>/<相対パス>          │
                    │  <archive>/.akasyx/archive.db  ← 正本    │
                    └───────────────────────────────────────────┘
                                    ^
                    verify.py ──────┘  保存フォルダを crawler で再スキャンして突き合わせ
                    dedupe.py ─────────  据え置いた重複を検証付きで削除
```

### 保存用フォルダの構造

```
<保存用フォルダ>/
├── .akasyx/
│   ├── archive.db          ← 正本（3テーブル。§8）
│   └── tmp/                ← 別ファイルシステム間コピーの一時領域（*.part）
├── 写真2024/               ← 投入元フォルダ名（--dest-subdir で変更可）
│   └── 旅行/IMG_0001.jpg   ← 投入元の相対パス構造をそのまま再現
└── 契約書.pdf              ← 投入元が単一ファイルの場合は直下
```

`archive.db` を保存フォルダの中に置くのは、**フォルダごと別ディスクへ移動・バックアップしても
DB が付いてくる**ようにするため。DB とファイル群が離れると正本を失う。

`.akasyx/` は crawler 呼び出し時に `--exclude '.akasyx/'` で除外する（verify で自分自身の DB を拾わないため）。

## 6. モジュール設計

### 6.1 main.py — エントリーポイント

サブコマンドを振り分ける。すべてのサブコマンドで共通して行うこと:

1. `config.parse_arguments()` → `setup_directories()` → `setup_logging()`
2. 保存用フォルダの存在確認と `archive.db` の初期化（無ければテーブルごと作成）
3. **`pending` 行の復旧処理**（§7.4）— どのサブコマンドでも先に走らせる
4. `ar_ingests` に実行行を作成し、終了時に `status` / 集計を書き戻す

### 6.2 config.py — 設定管理

```python
@dataclass
class DetectorConfig:
    mode: str                       # add / verify / delete-duplicates / report
    archive_root: str               # 保存用フォルダ（絶対パス）
    source_path: str | None = None  # 投入元（add のみ）
    dest_subdir: str | None = None  # 保存先の第1階層名（既定: 投入元フォルダ名）
    crawler_repo: str | None = None # crawler リポジトリのパス（既定: 兄弟の ../akasyx_crawler）
    db_dir: str = <repo>/dist/db    # crawler 出力先
    log_dir: str = <repo>/dist/log
    dry_run: bool = False
    min_size: int = 1               # これ未満は移動しない（0 バイト除外の実装 — §7.1）
    with_meta: bool = False         # crawler に形式別メタデータ抽出をさせる
    follow_symlinks: bool = False
    prune_empty_dirs: bool = False  # 移動後に空になった投入元ディレクトリを削除
    # verify
    flag_quarantine: list[str] = [] # missing / unregistered / archive_duplicate / hash_mismatch
    # delete-duplicates
    ingest_id: int | None = None    # 対象を特定の取り込み実行に絞る
    trash_dir: str | None = None    # 指定時は削除せずここへ退避
    assume_yes: bool = False        # 未指定なら一覧表示のみで削除しない
```

`app_version()` は crawler と同一実装（リポジトリルートの `version.txt` を読み、
読めなければ `"0.0.0"`）。`repo_root()` は `main.py` の位置（`detector/`）の1階層上。

### 6.3 database.py — archive.db の接続

crawler の `database.py` と同じ方針（`Base.metadata.create_all()` による冪等な作成、
`index=True` 宣言から索引を導出して二重管理しない）。接続先は
`<archive_root>/.akasyx/archive.db` に固定する。

SQLite の設定として次を有効にする:

| PRAGMA | 値 | 理由 |
|---|---|---|
| `journal_mode` | `WAL` | 移動処理中の頻繁な commit に強い |
| `synchronous` | `FULL` | **クラッシュ時に pending 行が失われると復旧できない**。速度より耐久性を優先 |
| `foreign_keys` | `ON` | SQLite は既定で OFF。FK 制約を実効にする |

### 6.4 crawler_client.py — crawler の起動と読み取り

```python
def run_crawler(target: str, config) -> CrawlerScan
def read_files(crawler_db: str, scan_id: int) -> Iterator[ScannedFile]
```

- 実行コマンド: `uv run main.py <target> --db-dir ... --log-dir ... --gitignore-mode off --no-meta`
  を `cwd = <crawler_repo>/crawler` で起動する（crawler は `__file__` からリポジトリルートを
  導出するため、cwd ではなく配置が効く。ただし `uv run` はプロジェクト解決に cwd を使う）
- crawler リポジトリが見つからない場合は、明示的なエラーで停止する
  （`--crawler-repo` での指定を促す）
- `ScannedFile` は §3 の列だけを持つデータクラス。**detector の判定ロジックは
  `ScannedFile` にしか依存させない**（テスト容易性のため — §14）
- 投入元が**単一ファイル**の場合: crawler はディレクトリ前提のため、
  親ディレクトリを対象に `--exclude` で他を除外するのではなく、
  **crawler を使わず detector が直接 stat + SHA-256 を計算する**（`utl/hashing.py`）。
  1ファイルのためにサブプロセスを起こす意味がなく、除外指定の取りこぼしリスクも避けられる

### 6.5 ingest.py — 判定ループ

`ScannedFile` を1件ずつ §7.1 の判定表にかけ、`ar_ingest_items` に記録する。
移動が必要なものだけ `mover.plan_and_move()` に渡す。
1件の失敗で全体を止めない（crawler §11 と同方針）。

### 6.6 mover.py — 移動とクラッシュ復旧

```python
def resolve_dest(archive_root, dest_subdir, rel_path, session) -> str   # 衝突回避込み
def plan_and_move(scanned, session, config, ingest_id) -> MoveResult
def recover_pending(session, config) -> RecoveryReport
```

§7.2 〜 §7.4 を実装する本体。**このモジュールだけが実体を書き換える権限を持つ**。

### 6.7 verify.py / 6.8 dedupe.py

§9 / §10 のとおり。

### 6.9 utl/hashing.py

`file_hash(path) -> str`（SHA-256、64KiB チャンクのストリーミング）。
crawler の `utl/fileinfo.file_hash` と**同一アルゴリズム・同一チャンク方針**で実装する
（crawler と別実装になるが、SHA-256 は結果が一致するため問題ない。
ここで独自の高速化を入れて結果が変わることのないよう、標準 `hashlib` のみを使う）。

## 7. 取り込みロジック（add）

### 7.1 判定表

crawler の `fs_files` から、**今回の scan_id で確認された `status='active'` の行**を取り出し、
1件ずつ次の順に判定する。上から順に評価し、最初に該当したもので確定する。

| # | 条件 | 判定 (`result`) | 実体の扱い | DB |
|---|---|---|---|---|
| 1 | `size < min_size`（既定 1 = **0 バイト**） | `skipped_empty` | **投入元に残す** | `ar_ingest_items` のみ |
| 2 | `filehash IS NULL` | `skipped_nohash` | 投入元に残す | `ar_ingest_items` のみ |
| 3 | 同一 `(filehash, hash_algo)` が `ar_archive_files` に status `stored` / `pending` で存在 | `duplicate` | **投入元に残す** | `ar_ingest_items`（`archive_file_id` に既存行を紐付け） |
| 4 | 上記以外 | `moved` | **保存フォルダへ移動** | `ar_archive_files` に新規行 + `ar_ingest_items` |
| — | 処理中に例外 | `failed` | 投入元に残す | `ar_ingest_items`（`message` に理由） |

**#1（0 バイト）について**: 内容が空のファイルはすべて同一ハッシュ
（`e3b0c442...`）になるため、放置すると「最初の1件だけが保存され、以降の全空ファイルが
重複扱い」という直感に反する結果になる。保存する価値もないため、**移動対象から外して
投入元に残す**方針とした。`--min-size 0` を指定すれば従来どおり内容一致として扱える。

**#2（ハッシュ無し）について**: crawler は読み取りエラー時に `filehash = NULL` で登録を続行する
（crawler `collector.py` の `_compute_hash`）。これを「新規」と誤判定すると、
重複が保存フォルダに紛れ込み、以後の判定が信用できなくなる。判定不能は必ず投入元に残す。

**#3 の照合条件**: `hash_algo` を条件に含める。crawler は local=SHA-256 / SharePoint=quickXorHash と
アルゴリズムが分かれるため、異なる algo 同士は照合してはならない（crawler §14）。
併せて `size` の一致も検算し、不一致なら `failed` として人に見せる
（SHA-256 が一致して size が違うことは通常あり得ないので、DB の破損か実装バグを疑う）。

**投入バッチ内の重複**: 判定と DB 登録を1件ずつ逐次 commit するため、
同じ投入元に同一内容のファイルが2つあれば、1件目が `moved`、2件目が `duplicate` になる。
特別な処理は要らない。

### 7.2 保存先パスの決定と衝突回避

```
保存先 = <archive_root>/<dest_subdir>/<crawler の path_rel>
```

- `dest_subdir` の既定は **投入元フォルダ名**（`os.path.basename(投入元の絶対パス)`）
- 投入元が単一ファイルの場合は `dest_subdir` を使わず `<archive_root>/<ファイル名>`
- `--dest-subdir NAME` で明示指定できる。`--dest-subdir ''` を渡すと保存フォルダ直下に
  投入元の相対構造をそのまま展開する

**衝突（同名・別内容）の解決**: `名前 (2).ext` → `名前 (3).ext` … の順に空きを探す。

- 拡張子の前に挿入する（`report.tar.gz` → `report.tar (2).gz` ではなく
  `os.path.splitext` ベースで `report.tar (2).gz` になる点は許容。複合拡張子は考慮しない）
- 判定は **実体の有無（`os.path.lexists`）と DB の `stored_path_rel` の両方**で行う。
  実体が無くても `pending` 行が予約している可能性があるため
- 大文字小文字を区別しないファイルシステム（macOS APFS の既定 / Windows）を考慮し、
  DB 側の突き合わせは `casefold()` して比較する
- 999 まで試して空きが無ければ `failed`（無限ループを作らない）

### 7.3 移動の3フェーズ

**この節が本設計の最重要箇所。** 「移動してから DB 登録」だと途中で落ちたときに
実体だけが保存フォルダに残って DB に無い状態（＝次回また移動しようとする）になり、
「DB 登録してから移動」だと移動失敗時に実体のない幽霊レコードが残る。
そこで **pending を先に書く3フェーズ**とする。

```
Phase 1（予約）
  ar_archive_files に status='pending' で INSERT
    filehash / hash_algo / size / stored_path_rel（確定済み）/ origin_path_abs
  ar_ingest_items に判定行を INSERT
  → commit（ここで落ちても Phase 0 の復旧が拾える）
  ※ UNIQUE(filehash, hash_algo) 違反で弾かれたら、それは同一内容が
     直前に登録されたということ。duplicate に倒してやり直す

Phase 2（移動）
  保存先の親ディレクトリを作成（os.makedirs(exist_ok=True)）
  同一ファイルシステムか判定: os.stat(src).st_dev == os.stat(archive_root).st_dev

  ├─ 同一FS  : os.replace(src, dst)        ← アトミック。1操作で完了
  │
  └─ 別FS    : shutil.copy2(src, <.akasyx/tmp>/<uuid>.part)
               → .part のハッシュを再計算して src のハッシュと照合
               → 不一致なら .part を削除して failed（元ファイルには触れない）
               → 一致したら os.replace(.part, dst)
               → ★ここで初めて os.unlink(src)

Phase 3（確定）
  dst を stat（同一FS 経路でも実施）し、size を照合
  status='stored' / verified_at を更新
  → commit
```

**別ファイルシステム間で「コピー → 検証 → 元を削除」の順を崩さないこと。**
`shutil.move` は内部で copy + delete を行うが、コピー内容の検証をしない。
ネットワークドライブや外付けディスクでは静かに壊れたコピーが起こり得るため、
`shutil.move` は使わず、上記の手順を自前で書く。

`os.replace` は移動先が既存でも**黙って上書きする**。§7.2 で衝突回避済みだが、
競合状態に備えて Phase 1 の DB 予約（`stored_path_rel` の UNIQUE）を
唯一の排他手段として扱い、実体側の存在チェックは補助とする。

### 7.4 クラッシュ復旧（起動時）

すべてのサブコマンドの開始時に、`ar_archive_files` の `status='pending'` 行を検査する。

| 状況 | 判断 | 処置 |
|---|---|---|
| 移動先に実体があり、ハッシュ一致 | 移動は完了していた | `status='stored'` に更新。元ファイルがまだ残っていれば（別FS コピー後の中断）ハッシュを照合してから削除 |
| 移動先に実体があり、ハッシュ不一致 | 別物が置かれている | `status='failed'`。人に提示（自動では消さない） |
| 移動先に実体が無く、元ファイルが残っている | 移動前に落ちた | pending 行を削除。次回の add で通常どおり処理される |
| 移動先にも元にも実体が無い | 判断できない | `status='failed'`。ログとレポートに出して人に見せる |

`.akasyx/tmp/*.part` は、起動時に**無条件で削除**する（作りかけのコピーであり、
`dst` へ `os.replace` された時点で `.part` は消えているため、残っていれば必ず失敗の残骸）。

### 7.5 実行サマリ

crawler の `[実行サマリ]` 形式を踏襲する。

```
[実行サマリ] 移動: 128件, 重複(据え置き): 47件, 空ファイル: 3件,
             ハッシュ不明: 1件, 失敗: 0件
```

併せて `dist/log/result_csv_YYYYMMDD_HHMMSS.csv` に1ファイル1行で
`name / source_path / result / size / stored_path_rel / message` を出力する。

**DB ファイル:** `<保存用フォルダ>/.akasyx/archive.db`

### ER 図


### `ar_archive_files.status`

| 値 | 意味 |
|---|---|
| `pending` | 移動を予約したが未完了（§7.3 Phase 1〜2 の途中） |
| `stored` | 保存フォルダに実体があり、DB と一致している（正常） |
| `missing` | DB にはあるが実体が無い（verify で検出。**削除はしない**） |
| `unregistered` | 保存フォルダに実体はあるが DB に無かった（verify が事後登録した行） |
| `quarantined` | 隔離フォルダへ移動済み（将来拡張。v0.1.0 では設定されない） |
| `failed` | 復旧で判断がつかなかった行（人の確認待ち） |

### `ar_archive_files.disposition` — 処置予定フラグ

verify が検出した異常に対し、**あとでまとめて処置するための予約**を立てる列。
v0.1.0 ではフラグを立てるところまでで、実移動は行わない（§16）。

| 値 | 意味 |
|---|---|
| `NULL` | 処置予定なし（既定） |
| `quarantine` | 別フォルダ（隔離先）へ移動する予定 |
| `adopt` | `unregistered` を正式登録（`stored`）にする予定 |
| `delete` | 削除する予定 |

### `ar_ingest_items.result`

| 値 | 発生元 | 意味 |
|---|---|---|
| `moved` | add | 保存フォルダへ移動した |
| `duplicate` | add | 内容重複のため**投入元に残した** |
| `skipped_empty` | add | 0 バイト（`min_size` 未満）のため移動しなかった |
| `skipped_nohash` | add | ハッシュが取得できず判定不能 |
| `failed` | add / 復旧 | 処理に失敗した（`message` に理由） |
| `archive_duplicate` | verify | 保存フォルダ**内**に同一内容が2つ以上あった |
| `hash_mismatch` | verify | DB と実体のハッシュが食い違う（人が書き換えた等） |
| `relocated` | verify | ハッシュは一致するが場所が変わっていた（`stored_path_rel` を更新済み）。`missing` 行に同一内容の実体が戻ってきた場合の復活もこれ |
| `missing` | verify | DB にはあるが実体が見つからなかった |
| `unregistered` | verify | 保存フォルダに実体はあるが DB に無かった |

### `ar_ingest_items.resolution` — 後始末の結果

| 値 | 意味 |
|---|---|
| `NULL` | 未処置（`delete-duplicates` の対象） |
| `deleted` | 投入元から削除した |
| `trashed` | `--trash-dir` へ退避した |
| `kept` | 人が「残す」と決めた（将来の UI 用。v0.1.0 では設定されない） |
| `gone` | 処置しようとしたら既に元ファイルが無かった |

### 索引と制約

| 索引 / 制約 | 目的 |
|---|---|
| `ar_archive_files(filehash, hash_algo)` **UNIQUE（部分索引: `status IN ('pending','stored')`）** | **重複判定の要**。実装にバグがあっても二重登録を DB が弾く。`missing` / `unregistered` を除外することで、消えたファイルと同内容のものを後から再登録できる |
| `ar_archive_files(stored_path_rel)` UNIQUE（部分索引: `status IN ('pending','stored','unregistered')`） | 保存先パスの二重予約を防ぐ |
| `ar_archive_files` の `lower(stored_path_rel)`（式索引） | 衝突回避（§7.2）の casefold 突き合わせ。SQLite の `lower()` で両辺を畳むため、Python 側の `lower()` と混ぜて非 ASCII で食い違うことがない |
| `ar_archive_files(status)` / `(disposition)` | verify・処置対象の絞り込み |
| `ar_ingest_items(ingest_id)` | 実行単位のレポート |
| `ar_ingest_items(filehash)` | ハッシュからの追跡 |
| `ar_ingest_items(result, resolution)` | `delete-duplicates` の対象抽出（`result='duplicate' AND resolution IS NULL`） |
| `ar_ingest_items(source_path_abs)` | 同一ファイルの判定履歴 |

部分 UNIQUE 索引は SQLite の機能であり、SQLAlchemy では
`Index(..., unique=True, sqlite_where=text("status IN ('pending','stored')"))` で宣言する。

## 9. 整合性チェック（verify）

保存フォルダは人が直接ファイルを消したり動かしたりできる。DB を正本とする以上、
**実体とのズレを検出する手段がなければ正本が腐る**。

### 手順

1. **保存フォルダ自身**を対象に crawler を実行する（`--exclude '.akasyx/'` を付与）
2. crawler の `fs_files` と `ar_archive_files`（`status IN ('pending','stored')`）を突き合わせる

| 状況 | 検出結果 | DB の更新 |
|---|---|---|
| DB にあり、同じパスに実体あり、ハッシュ一致 | 正常 | `verified_at` を更新 |
| DB にあるが実体が無い | `missing` | `status='missing'`（**行は消さない**。履歴として残す） |
| DB にあり、実体はあるがハッシュが違う | `hash_mismatch` | `ar_ingest_items` に記録。**DB のハッシュは書き換えない**（何が正しいか機械には決められない） |
| DB にあるハッシュの実体が、別のパスで見つかった | `relocated` | `stored_path_rel` を実際の場所に更新し、`ar_ingest_items` に記録 |
| 実体はあるが DB に無い | `unregistered` | `ar_archive_files` に `status='unregistered'` で新規行を作成（`ingest_id` は今回の verify 実行） |
| 保存フォルダ内に同一ハッシュが2つ以上 | `archive_duplicate` | `ar_ingest_items` に記録。2件目以降は `unregistered` 扱い（部分 UNIQUE 索引に抵触しない） |

`missing` と `relocated` は区別が必要なため、**先に全件のハッシュ表を作ってから**判定する
（パス単位で逐次判定すると、移動されたファイルを「missing + unregistered」の2件に割ってしまう）。

### 処置予定フラグの付与

```bash
uv run main.py verify <保存用フォルダ> --flag-quarantine unregistered archive_duplicate
```

指定した種別に該当する `ar_archive_files` 行の `disposition='quarantine'` を立てる。
**このコマンドはファイルを一切動かさない。** 実際に隔離フォルダへ移すのは将来対応（§16）で、
その際は `disposition='quarantine'` の行だけを対象にすればよい。

`--flag-quarantine` で指定できる種別: `missing` / `unregistered` / `archive_duplicate` / `hash_mismatch`

（`missing` は実体が無いので移動しようがないが、「消えた記録を別扱いにしたい」という
用途があり得るためフラグの対象には含める。実移動の実装時に無視される。）

## 10. 重複の後始末（delete-duplicates）

`add` で投入元に据え置いた重複を、**検証付きで**削除する。

### 対象

`ar_ingest_items` のうち `result='duplicate' AND resolution IS NULL`。
`--ingest-id N` で特定の取り込み実行に絞れる（既定は全件）。

### 削除前の2点検証（必須）

1件ごとに、次の**両方**を満たしたときだけ削除する。1つでも欠ければスキップして理由を記録する。

1. **投入元のファイルが存在し、現在のハッシュが記録と一致する**
   （判定後にユーザーが中身を差し替えた可能性がある）
2. **対応する `ar_archive_files` 行が `status='stored'` で、保存フォルダに実体があり、
   そのハッシュが一致する**
   （保存フォルダ側が消えていたら、投入元が最後の1本かもしれない）

検証は毎回ハッシュを再計算する。時間はかかるが、**削除は取り返しがつかない**ため省略しない。

### 安全側の既定動作

| 指定 | 動作 |
|---|---|
| （何も付けない） | **一覧を表示するだけで削除しない**（実質ドライラン）。件数と合計サイズを出す |
| `--yes` | 実際に削除する |
| `--trash-dir DIR` | 削除ではなく DIR へ移動する（`--yes` と併用。ディレクトリ構造は投入元の相対パスを再現） |
| `--prune-empty-dirs` | 削除の結果、空になった投入元ディレクトリを削除する（投入元ルート自体は消さない） |

処理後、`ar_ingest_items.resolution` に `deleted` / `trashed` / `gone` を、
`resolved_at` に日時を書く。一度処置した行は次回以降の対象から外れる。

## 12. エラーハンドリング

crawler §11 の方針（1ファイルの失敗で実行全体を止めない）を踏襲する。

| 事象 | 扱い |
|---|---|
| **保存フォルダと投入元が入れ子** | **事前チェックで拒否（終了コード 3）**。保存フォルダが投入元の配下にあると自分自身を取り込む。`os.path.commonpath` で双方向に判定する |
| crawler リポジトリが見つからない | 事前チェックで拒否（3）。`--crawler-repo` を促す |
| crawler のスキャンが `completed` でない | 事前チェックで拒否（3）。§3 のとおり不完全な走査では取り込まない |
| 保存フォルダが書き込み不可 | 事前チェックで拒否（3） |
| ディスク容量不足（別FS コピー時） | その1件を `failed`。`.part` を削除。**元ファイルには触れない**。以降の処理は続行するが、同じエラーが3回続いたら中止する |
| 移動先の親ディレクトリ作成に失敗 | その1件を `failed` |
| 移動後のハッシュ検証が不一致 | その1件を `failed`。`.part` を削除。元ファイルは残す。ログに警告 |
| 元ファイルの読み取り権限が無い | その1件を `failed` |
| `KeyboardInterrupt` | 現在の1件を完了させてから停止し、`ar_ingests.status='interrupted'`。pending 行は次回起動時の復旧が拾う |
| DB ロック（他プロセスが同じ保存フォルダを操作） | WAL でも書き込みは排他。**保存フォルダ単位のロックファイル**（`.akasyx/lock`）で多重起動を検出して拒否する |

ログはファイル（DEBUG）+ コンソール（INFO）の2系統。crawler の `setup_logging` と同形式で
`dist/log/detector<YYYYMMDD>.log` に出力する。

## 14. テスト方針

**crawler は CI 環境に存在しない**（別リポジトリ）。したがって、
crawler への依存は `crawler_client.py` に閉じ込め、
**判定ロジックは `ScannedFile` のリストにのみ依存させる**。

テストは crawler を一切必要としない。テスト用フィクスチャは `crawler_client` の
**`run_crawler` と `resolve_crawler_repo` の両方**を差し替え、さらに設定の既定値
`crawler_repo` を必ず存在しないパスにする。`run_crawler` だけを差し替えると、
`preflight` が別途呼ぶ `resolve_crawler_repo` が実機の兄弟ディレクトリを見つけて
しまい、**開発機では通るが CI では落ちるテスト**になる（2026-08-30 に実際に発生）。

| 種別 | 内容 |
|---|---|
| 判定ロジック | `ScannedFile` を手で組み立て、§7.1 の判定表を全分岐（0バイト / ハッシュ NULL / 既存重複 / 新規 / size 不一致）で検証 |
| 衝突回避 | 同名・別内容を3つ投入し、`名前 (2)` / `名前 (3)` になること。大文字小文字を区別しない FS を想定した casefold 比較 |
| 3フェーズ移動 | `tmp_path` 上で実行。Phase 2 の直後に例外を注入し、復旧処理が `stored` に収束することを確認 |
| 別FS 経路 | `os.stat().st_dev` をモンキーパッチして「別FS」を強制し、copy → 検証 → unlink の順序と、検証失敗時に元ファイルが残ることを確認 |
| クラッシュ復旧 | §7.4 の4パターンをそれぞれ DB と実体の状態を作って再現 |
| UNIQUE 制約 | 同一ハッシュを2度 INSERT して部分 UNIQUE 索引が弾くこと。`missing` 行とは衝突しないこと |
| verify | missing / unregistered / relocated / hash_mismatch / archive_duplicate の5パターン。特に「移動されたファイルが missing + unregistered に割れない」ことを確認 |
| delete-duplicates | 2点検証のどちらかを崩したときに削除されないこと（**最重要**）。`--yes` 無しで削除されないこと |
| 入れ子チェック | 保存フォルダが投入元の配下 / 投入元が保存フォルダの配下 の双方で拒否されること |
| crawler 連携 | 実 crawler を使う統合テスト。`--crawler-repo` が解決できない環境では `pytest.mark.skipif` でスキップ |

## 15. 設計上の制約と注意事項

- **保存フォルダと投入元を入れ子にできない。** 事前チェックで拒否する（§12）
- **0 バイトファイルは保存フォルダに入らない**（決定事項）。投入元に残る。
  内容一致として扱いたい場合のみ `--min-size 0`
- **ハッシュが取れなかったファイルは移動しない。** 投入元に残り、レポートに出る
- 別ファイルシステムをまたぐ移動は、コピー + ハッシュ再計算のぶん時間とディスクを消費する。
  同一ディスク内であれば `os.replace` で瞬時に終わる
- **ハードリンク**: 同一 inode の2ファイルは同じ内容なので、片方が移動され、
  もう片方は重複として投入元に残る。リンク関係は保存フォルダに引き継がれない
- **シンボリックリンク**: crawler の既定に従い追跡しない。リンク自体は
  ハッシュ計算対象にならず `skipped_nohash` になる可能性がある
- **大文字小文字を区別しないファイルシステム**（macOS APFS 既定 / Windows）では、
  `A.txt` と `a.txt` が同一パスとして衝突する。§7.2 の衝突判定は casefold して行う
- SHA-256 の衝突は現実的に無視できるが、`size` の一致も検算し、
  食い違ったら `failed` として人に見せる（DB 破損か実装バグの兆候）
- crawler が SharePoint（quickXorHash）に対応すると `hash_algo` が混在する。
  照合は同一 algo 同士のみ。またリモートの実体は移動できないため、
  **v0.1.0 の取り込み対象は `source_type='local'` に限る**
- 保存フォルダに対する多重起動は `.akasyx/lock` で拒否する。
  複数プロセスが同時に移動すると、部分 UNIQUE 索引が守れても実体の整合が崩れる
- `archive.db` は保存フォルダの中にあるため、**保存フォルダを丸ごとコピーすると
  DB も複製される**。コピー先で add を実行すると2つの正本が分岐する点に注意
- crawler の DB（`dist/db/file_inventory.db`）は作業用であり、消しても
  保存フォルダの正本には影響しない。ただし crawler の差分スキャンが効かなくなり
  次回が遅くなる
