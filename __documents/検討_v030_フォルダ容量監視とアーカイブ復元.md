# 検討メモ v0.3.0 — フォルダ容量監視とアーカイブ（退避）と復元

> このファイルは **検討中の下書き**であり、確定仕様ではない。決めたことは章末の
> 「未決事項」から本文へ昇格させ、確定後に `設計書_v030_…` として正式化する。

## 0. この機能の一言まとめ

指定したフォルダ（＝**監視フォルダ / working フォルダ**）を定期的に見張り、
**合計容量が上限を超えたら、古いものから Archive フォルダへ退避**して容量を維持する。
退避したファイルは **退避時のフォルダ階層のまま画面で一覧・可視化**でき、選ぶと
**元の階層のまま元の監視フォルダへ復元**できる。

要するに **「ホット層（監視フォルダ）／コールド層（Archive）の階層ストレージ（tiering）＋復元」**。
容量が張り付くフォルダ（Downloads、録画、素材置き場など）を、手を触れずに一定容量に保つ。

### 確定事項（2026-09-16 / 対話で決定）

| # | 決定 | 備考 |
|---|---|---|
| A | **退避層の重複排除はしない。1:1 でそのまま退避する** | 復元忠実性を最優先。dedup は将来（§1 の合流点） |
| B | **退避方針の既定は LRU（最終アクセス）** | ただし **Windows / Linux / macOS の 3 OS 対応**が前提。atime が各 OS で不安定なため §5 で移植性を設計する |
| C | **定期スイープはアプリ内スケジューラで回す** | Electron アプリが担う。OS の launchd/cron には依存しない（§6） |
| D | **容量計測・ランキング・ハッシュは crawler を使う**（内蔵しない） | crawler は `size`/`atime`/`mtime` を出し `--no-hash` の高速パスもある。**Windows/Linux でも動くことが必須**（§4-4） |
| E | **pin（退避保護）を v0.3 に入れる** | 指定した file/folder は容量超過でも退避しない。working フォルダの誤退避防止（§5.1） |
| F | **退避の単位はフォルダ単位（配下ごと一緒に移す）** | フォルダを退避するとき配下の file/folder も同じバッチで移動。**成立条件: フォルダが cold なのは配下が全て cold のときだけ**（§5.2） |
| G | **容量は指定容量 C の ±5%: 退避目標=C−5%・アラート=C+5%** | スイープは C−5% まで（超過分だけ）退避。C+5% まではアラートなし、超えて下げ切れない時だけ通知（§5.3） |
| H | **OS 特有の隠しファイル/フォルダは退避しない（消えてよい）** | `.DS_Store`/`._*`/`.Spotlight-V100` 等は Archive に移さず、空フォルダ掃除で消えてよい（§5.4） |

> **新たに確定した制約: ターゲット OS は Windows / Linux / macOS の 3 つ。**
> 以降の設計はパス区切り・大文字小文字・atime 更新規則・常駐方法をすべて 3 OS 前提で書く。
>
> **crawler の 3 OS 対応状況（2026-09-16 調査）**: crawler は移植性を意図した実装
> （`resolve_times` が macOS=st_birthtime / Windows=st_ctime / Linux=None を出し分け、
> atime も取得。依存は sqlalchemy + pathspec + 任意 meta ライブラリで OS 固有ライブラリ無し）。
> **ただし CI は crawler・detector とも `ubuntu-latest` のみ**で、Windows/macOS 上の
> 実動作は自動テストで未検証。3 OS 必須なら **CI に windows/macos マトリクスを足すのが前提条件**（§10）。

## 1. 既存機能との関係（最重要の設計判断）

結論: **既存の重複排除アーカイブ（`add`）とは別のサブシステムとして作る。**
インフラ（正本 DB・3フェーズ安全移動・crawler・ロック・Electron 殻）は再利用するが、
**保存レイアウトと意味づけは分ける。**

| | 既存 `add`（重複排除アーカイブ） | 新機能（容量監視・退避） |
|---|---|---|
| 目的 | 内容重複のない**正本集合**を作る（一方向の取り込み） | 監視フォルダを**一定容量に保つ**（可逆な tiering） |
| 重複の扱い | 重複は移動せず投入元に残す | **重複でも退避する**（1:1 で退避しないと復元できない） |
| 保存レイアウト | `YYYY-MM/<subdir>/<相対>/…`（**再編成**する） | **監視ルートからの相対パスをそのまま保持**（復元のため） |
| 元パスへの復元 | 想定しない（正本は月別に再編成済み） | **中核機能**。退避時の絶対パスへ戻す |
| 削除 | `delete-duplicates` で据え置き重複を消す | 退避＝移動なので元フォルダから消える（復元で戻る） |

### なぜ混ぜてはいけないか

- 既存アーカイブは **dedup（重複排除）** が前提。同じ内容は 1 つしか持たない。
  → **復元のためには 1:1 の実体が要る**ので、dedup と復元忠実性は本質的に衝突する。
- 既存アーカイブは月別に**再編成**する（`YYYY-MM/`）。復元先の元階層を保証しない。
- したがって「退避層」は **監視ルート相対パスを鍵にした別レイアウト**で持つのが正解。

> **将来の合流点（v0.3 では踏み込まない）**: 退避層でも内容重複を潰したいなら、
> content-addressed 実体 + ハードリンク（参照カウント）にすれば、復元忠実性を保ったまま
> 重複排除できる。ただし macOS/別FS/同期ツールとの相性検証が要るので**将来拡張**に置く。
> v0.3 は**素朴な 1:1 移動**で「確実に戻せる」ことを最優先する。

## 2. スコープ

### やること（v0.3.0 案）
- 監視フォルダの**登録**（ルート・上限容量・Archive 先・退避方針）
- **定期スイープ**（`sweep`）: 容量を測り、上限超過なら下限まで退避
- 退避の**実体移動**は既存の 3フェーズ安全移動（§7.3）を再利用
- 退避記録を DB に残し、**元階層を復元できる情報**（監視ルート相対パス）を保持
- 退避ファイルの**ツリー可視化**（Electron）と**復元**（`restore`）
- 復元の衝突・検証（戻す先に同名がある／内容が変わっている場合の安全策）
- ドライラン（`sweep --dry-run` で「何が退避されるか」を見るだけ）

### やらないこと（v0.3.0 案）
- **リアルタイム監視**（FSEvents / inotify / ReadDirectoryChangesW）。v0.3 は
  **アプリ内スケジューラのスイープ**のみ（決定 C）。常駐監視は将来拡張
  （既存ツールが crawler ベースのバッチ志向なため段階導入する）
- 退避層の重複排除（§1 の将来合流点）
- クラウド／SharePoint 上のフォルダの監視（実体を移動できない）
- 圧縮・アーカイブ化（zip 等）。退避はあくまで**別ディスク/別フォルダへの移動**

## 3. 退避層のレイアウト（復元忠実性の要）

Archive（コールド層）フォルダ内に、**監視フォルダごと**・**スイープ（退避バッチ）ごと**に
区切り、その下は**監視ルートからの相対パスをそのまま**再現する。

```
<Archive>/
├── .akasyx/                      ← 既存と同じメタ領域（archive.id・tmp・lock を流用）
└── _evicted/
    └── <monitor-uid>/            ← 監視フォルダの識別子（複数の監視フォルダを混ぜない）
        └── 2026-09-16T0120Z/     ← 退避バッチ（スイープ時刻。UTC）
            ├── 旅行/IMG_0001.jpg  ← 監視ルート相対パスをそのまま
            └── 素材/logo.png
```

- **バッチ（時刻）で区切る**理由: 「その時のフォルダ階層の状態」を保存するため。
  同じ相対パスが別スイープでまた退避されても、バッチが違えば衝突しない。
- 相対パスをそのまま持つので、**DB が壊れても実体だけ見れば元階層が分かる**（自己記述的）。
- ただし**正本は DB**（下記テーブル）。実体レイアウトは人間可読の冗長コピーと考える。

## 4. データモデル（追加テーブル案）

既存の `Archive`（`ar_archives`）を**コールド層の場所登録に再利用**（uid・`.akasyx/archive.id`
・ロックがそのまま効く）。その上に監視と退避の 3 テーブルを足す。

| テーブル | 役割 |
|---|---|
| `ar_monitors` | 監視フォルダ 1 件 = 1 行。ルート・上限・下限・方針・Archive 先・有効フラグ |
| `ar_sweeps` | スイープ（退避バッチ）1 回 = 1 行。`ar_ingests` に mode=`sweep` を足す案でも可 |
| `ar_evicted_files` | 退避したファイル 1 件 = 1 行。**復元の鍵**（監視ルート相対パス）を持つ |

### `ar_monitors`（案）
| 列 | 内容 |
|---|---|
| id / uid | 監視フォルダの識別子（フォルダ移動に耐える） |
| root_abs | 監視フォルダの現在の絶対パス |
| archive_id | 退避先（FK → ar_archives） |
| capacity_bytes | **指定容量 C**（ユーザーが指定する 1 つの基準値。§5.3） |
| band_pct | 許容バンド（既定 **5%**）。退避目標 = C×(1−band) / アラート閾値 = C×(1+band)（§5.3） |
| policy | 退避順の方針（既定 `lru` = `max(atime,mtime)` 昇順 / 併用 `largest`。§5） |
| unit | 退避の単位（既定 `folder` = フォルダ単位・配下ごと。§5.2 決定 F。`file` も選べる余地） |
| min_age_days | この日数より新しいものは退避しない（作りたてを即退避しない保護） |
| enabled / last_swept_at / created_at | 運用フラグと履歴 |

### `ar_evicted_files`（案）
| 列 | 内容 |
|---|---|
| id / monitor_id / sweep_id | 所属 |
| origin_rel | **監視ルートからの相対パス（POSIX）＝復元先の鍵** |
| is_dir | 空ディレクトリの行か（1 なら実体無し・復元時にフォルダを作るだけ。§5.2 空フォルダ保存） |
| origin_abs_at_evict | 退避時点の絶対パス（監査用） |
| size / filehash / hash_algo | 復元後検証・監査用（is_dir 行では null） |
| origin_atime / origin_mtime / origin_created_at | LRU 鍵・可視化の並び・元の日時保持 |
| stored_path_rel | Archive 内の相対パス（§3。is_dir 行では null 可） |
| status | `evicted`（退避中）/ `restored`（復元済み）/ `missing`（実体消失）/ `failed` |
| evicted_at / restored_at | 履歴 |

- **UNIQUE 制約**: `(monitor_id, origin_rel)` は status=`evicted` の部分索引で一意にする。
  → 同じ元パスが二重に「退避中」にならない（既存 §8 の部分 UNIQUE と同じ手法）。
- **フォルダ単位退避（§5.2）**は「同じ sweep_id を共有する複数行（＋ is_dir 行）」として表現し、
  ツリー/復元は `origin_rel` のプレフィックスで束ねる。専用の「フォルダ行」テーブルは持たない。

### pin の保存（§5.1・決定 E）
- **マーカーファイル方式**はスイープ時に監視ルートを歩いて `.akasyxkeep` を検出 → 除外集合に入れる
  （DB を持たない）。
- **DB フラグ方式**を足すなら `ar_pins`（monitor_id, origin_rel, created_at）の小テーブルで持ち、
  スイープが両方を除外集合にマージする。v0.3 最小実装はマーカー方式のみでも成立。

## 5. 退避方針（どれを・どの単位で退避するか）

### 何から退避するか（policy）＝ **既定 LRU（決定 B）**
最終アクセスが古いものから退避する。ただし **atime は 3 OS のいずれも既定では信用しづらい**
ため、素の atime だけに頼らず「移植可能な LRU」を組む。

**各 OS の atime 更新の実情**
| OS | 既定の挙動 | 影響 |
|---|---|---|
| macOS (APFS) | 読み取りで atime 更新するが遅延・粗い | だいたい使えるが精度は粗い |
| Linux | 近年の既定は `relatime`（前回 atime < mtime か 24h 経過で更新） | **粗い LRU としては十分実用**。`noatime` マウントだと全く更新されない |
| Windows (NTFS) | Vista 以降 `NtfsDisableLastAccessUpdate` 既定で**更新オフ**が多い | 素の atime は当てにならない。有効化 or フォールバックが必要 |

**crawler が既に atime を出す（好都合な事実）**
crawler の `fs_files` は `accessed_at`(atime) / `modified_at`(mtime) / `size` を持ち、
`--no-hash` でハッシュ計算を省いた高速インベントリも取れる（crawler で確認済み 2026-09-16）。
→ **LRU のランキングに必要な情報は crawler からそのまま読める**。detector 側で stat し直す
必要はなく、容量計測とランキングは crawler `--no-hash` の 1 パスで賄える（§6）。

**移植可能な LRU の実装方針**
1. ランキング鍵は **`access_key = max(atime, mtime)`**（両方 crawler の `fs_files` 由来）。
   - こうすると「最近“変更”したが atime は古い/止まっている」ファイルを誤って退避しない。
   - atime が全く動かない環境では実質 mtime ベースに縮退する（安全側）。
2. スイープ時に **atime が更新される環境かを検出**し、止まっていそうなら
   「LRU が mtime 近似で動作中」と**明示ログ**（沈黙で精度劣化させない — vault ルール）。
   - Windows は `NtfsDisableLastAccessUpdate` を読む／Linux はマウントオプション（noatime）を見る。
3. **より正確な LRU が要るなら「自前アクセス追跡」**（将来）: リアルタイム監視（§2 将来）を
   入れた時に open/read を観測して DB に `last_access` を持てば、OS の atime 設定に依存しない。
   v0.3 は 1〜2 の OS ネイティブ atime + フォールバックで始める。
4. 補助 policy（併用可）: `largest`（大きいもの優先）を tie-break や代替として用意。

- 併用: 「min_age_days より新しいものは退避しない」を足切りにした上で `access_key` 昇順にソート。

### 5.1 pin（退避保護）＝ **v0.3 に入れる（決定 E）**
指定した file / folder を**容量超過でも退避対象から外す**。working フォルダの誤退避防止。

- **指定方法（両対応を想定）**:
  - **マーカーファイル `.akasyxkeep`**: 守りたいフォルダに空ファイルを置くと、そのフォルダ配下を
    pin 扱い。フォルダを見れば分かる／Git 等で共有できる。
  - **DB フラグ**: UI でファイル/フォルダを選び「保護」。画面で一元管理。
  - どちらも最終的に**「退避候補から除外する集合」**に落ちる。v0.3 の最小実装は
    マーカーファイル方式を先に入れると軽い（DB フラグは UI と一緒に足す）。※未決 §10-4。
- **pin の伝播（フォルダ単位退避との整合）**: 配下に pin された file が 1 つでもあれば、
  その**祖先フォルダは丸ごと退避しない**（§5.2 の cold 判定に組み込む）。
- **復元直後の保護**: 復元したファイルは「復元後 N 時間 / min_age_days」だけ暗黙 pin 相当にして、
  次スイープで即退避し返さない（無限ループ防止）。

### 5.2 退避の単位 = **フォルダ単位（決定 F）**
フォルダを退避するとき、**配下の file / folder も同じスイープ（同じバッチ）で一緒に移す**。
階層がバラけず、可視化・復元が「そのフォルダごと」で直感的になる。

**成立条件（最重要ルール）**: フォルダを退避してよいのは、**配下が全て cold のときだけ**。
- フォルダの LRU 鍵 = **配下ファイルの `access_key`（=max(atime,mtime)）の最新値（max）**。
  → 配下に 1 つでも最近使ったファイルがあれば、そのフォルダは cold ではなく、退避しない。
- 配下に pin / min_age 内 / OS ジャンク以外の「移せない理由」があるフォルダも退避しない（§5.1）。

**粒度は葉フォルダから畳む**:
- 単位は「ファイルを直接含むフォルダ（葉）」を基本にし、葉が cold なら葉ごと退避。
- 監視ルート直下の巨大サブツリーをいきなり移すと**過剰退避**になるため、深い方（葉）から
  評価して上へ畳む。ある親の配下の葉が全て退避され切ったら、親も空フォルダとして畳める。

**過剰退避の許容**:
- フォルダ単位だと target ちょうどには止まれない。**target を多少下回る（余分に空く）のは許容**する
  （害が小さい）。厳密に合わせたい場合の「最後の微調整だけファイル単位」は将来オプション。

**空フォルダの保存（復元忠実性）**:
- フォルダごと移すなら、**中身が空のサブフォルダも復元時に再現**できるよう記録する
  （ファイル行だけだと空ディレクトリが失われる）。`ar_evicted_files` に `is_dir` 行を持たせるか、
  バッチに畳んだディレクトリ一覧を残す（§4 の未決に反映）。

### 5.3 容量モデル ±5%（決定 G・確定）
ユーザーは **指定容量 C を 1 つだけ**指定する。`band_pct`（既定 5%）が **退避の目標**と
**アラート閾値**の両方を決める。C = 100GB の例で:

| しきい値 | 値（C=100GB） | 意味 |
|---|---|---|
| **退避目標 = C×(1−band)** | **95GB** | スイープはここまで下げる（＝運用上の実質上限）。**超えた分だけ**退避する |
| **アラート閾値 = C×(1+band)** | **105GB** | ここまでは**アラートを出さない**。膨らみは正常とみなす |

- **退避の動き**: スイープ時に使用量 > 95GB なら、**超過分だけ**を cold な葉フォルダから退避して
  95GB 付近まで戻す（§5.2）。フォルダ単位なので 95GB を多少下回るのは許容（過剰退避許容）。
- **±5% の帯の意味**: フォルダや大きいファイルがあるため、実使用量は
  スイープ間で **95GB〜105GB を行き来してよい**（105GB まではアラートなし）。
  定期スイープ（§6）ごとに 95GB へ引き戻す。**単一目標でもスイープが定期実行なのでスラッシングしない**
  （退避頻度はスイープ間隔で頭打ちになる。二段 watermark を別途設けなくてよい）。
- **アラート**: スイープしても・スイープ間で **105GB を超えて下げ切れない**ときだけ通知する。
  原因は「pin/hot なファイルが多くて空けられない」「単一ファイルが空き容量より大きい」等。
  → 容量維持の失敗を沈黙させない（vault ルール「成否は証拠で報告」に対応）。
  アラートの出し先はアプリ内スケジューラ（決定 C）の UI 通知／ログ。
- 復元直後は §5.1 の暗黙 pin で即退避し返さない。

### 5.4 OS 特有の隠しファイル/フォルダは退避しない（消えてよい）
`.DS_Store` / `._*`（AppleDouble）/ `.Spotlight-V100` / `.Trashes` / `.fseventsd` /
`.DocumentRevisions-V100` / `Thumbs.db` / `desktop.ini` などの **OS/Finder が生成するメタデータは
退避対象にしない**（Archive に移さない）。容量計算からも実質除外する（元々小さい）。

- これらは**退避せず監視フォルダ側に残す**。ただしフォルダを退避して空になった際、
  既存 `prune_empty_dirs`（`JUNK_FILES` しか無いフォルダを空とみなして削除）と同様に
  **一緒に消えてよい**（ユーザー了承済み。復元対象にもしない）。
- 既存の `config.OS_JUNK_FILES` を土台にし、macOS 固有の隠しフォルダ名を足した除外集合を使う。
  crawler 側の `.gitignore` 除外とも二重に効く（crawler は既定でこれらを走査対象外にできる）。

## 6. スイープ処理の流れ（`sweep`）

1. **容量計測＋ランキング（安いパス）＝ crawler `--no-hash`（決定: crawler を使う）**:
   監視ルートを crawler で差分スキャン（`--no-hash`）し、`fs_files` から
   `size` / `accessed_at` / `modified_at` を取得。ここでハッシュは取らない（毎回の全ハッシュは高コスト）。
   crawler は差分スキャンなので 2 回目以降は速く、移動・削除も追従する。
2. 合計 ≤ **退避目標 C×(1−band)=C−5%** なら**何もせず終了**（履歴だけ残す）。
3. 超過なら、**cold な葉フォルダ**を候補にする（§5.2）: 葉フォルダごとに配下の
   `access_key` の **最新値（max）** を出し、pin・min_age・OS ジャンクを除外。
   「配下が全て cold」な葉フォルダだけを、そのフォルダ鍵の昇順（古い順）に並べる。
4. 合計が **C−5% を下回るまで**、候補フォルダを先頭から**退避リストに積む**（＝超過分だけ・§5.3）。
   フォルダ単位・配下ごと。葉が退避され切って空になった親は上へ畳んで空フォルダとして扱う。
5. 退避対象フォルダ配下のファイル**だけ**ハッシュを取り（crawler に対象パスを渡す or 移動時に
   detector が計算。復元検証と DB 記録用）、**3フェーズ安全移動**（§7.3）で
   `<Archive>/_evicted/<uid>/<batch>/<origin_rel>` へ移動。空サブフォルダは `is_dir` 行で記録（§4）。
6. `ar_evicted_files` に記録。移動後サイズ検証まで既存 mover を流用。
7. `--prune-empty-dirs` 相当で、退避後に空になった監視フォルダ側の枝を掃除（任意）。
8. **アラート判定**: 退避後もなお合計 > **アラート閾値 C×(1+band)=C+5%** なら通知（§5.3）。
   候補が尽きた（pin/hot ばかり）・単一ファイルが空きより大きい等で下げ切れない兆候。
9. **取得ステータスを必ず残す**（ok/失敗/スキップ件数・退避前後の合計・アラート有無）。失敗を沈黙させない
   （※ vault ルール「実行・取得の成否は証拠で確認」に対応。空振りを健全と誤認しない）。

- **dry-run**: 4 まで実行して「退避予定リスト・解放見込みバイト」を出すだけ。実体も DB も触らない。
- **定期実行 = アプリ内スケジューラ（決定 C）**: Electron アプリが `setInterval` 相当で
  各監視フォルダの `sweep` を子プロセス起動する（既定 例: 1 時間毎、監視フォルダ毎に設定可）。
  - **3 OS 共通**で同じ仕組みが動く（launchd/cron/タスクスケジューラの OS 差を避けられる）。
  - **アプリ起動中しか回らない**のが弱点。対策:
    - **起動時に必ず 1 回スイープ**（前回からの取りこぼしを回収）。
    - **トレイ常駐 + ログイン時自動起動**（`app.setLoginItemSettings`。Win/mac 対応、
      Linux は autostart `.desktop`）を任意で有効化 → 実質バックグラウンド常駐。
    - スイープは**多重起動しない**（既存 §12 のロックで保証）。
  - リアルタイム監視は将来（§2）。当面はこのスケジュール・スイープで十分。

## 7. 復元（`restore`）

- 入力: 退避 ID（複数）／バッチ／`origin_rel` プレフィックス（フォルダ単位）。
- 復元先 = `monitor.root_abs` + `origin_rel`。
- **衝突**: 復元先に既に実体がある場合:
  - 内容ハッシュが同じ → 復元済みとみなしスキップ（実体は消さない）。
  - 内容が違う → 既存 `pick_free_name`（`名前 (2).ext`）で退避せず**別名で戻す**か、
    人に確認（UI）。**上書きは既定でしない**（既存の安全原則を踏襲）。
- 復元も**3フェーズ**で戻し、戻した後にハッシュ/サイズ検証 → status=`restored`。
- 復元で quota を超え得るが、**その場で退避し返さない**（無限ループ防止）。次スイープに委ねる。
  ただし復元直後は §5 の保護で即退避対象から外す。

## 8. 画面（Electron）— 可視化と復元

既存方針（§16「UI とロジックの境界を CLI に固定」）を踏襲。UI は CLI を子プロセス起動し、
結果は SQLite / JSON を読む。CLI に `--json` 出力を足すのが前提。

### 画面構成（案）
- **左ペイン**: 監視フォルダ一覧。各行に**使用量バー（used / quota）**と最終スイープ時刻。
- **メインペイン**: 選んだ監視フォルダの**退避ファイルのツリー**。
  - `origin_rel` からフォルダ階層を復元して描く（＝「その時の階層の状態」）。
  - バッチ（退避日時）でフィルタ。フォルダは「一部退避/全部退避」を色/バッジで示す。
  - ノード（ファイル/フォルダ）を選択 → **「元のフォルダに復元」ボタン**。
- **フッター/詳細**: 選択の合計サイズ、復元先パス、衝突有無のプレビュー。

### データの流れ
- ツリーは `evicted list --monitor <uid> --json` の出力から**レンダラが構築**。
- 復元は選択 ID を集めて `restore --ids …` を子プロセス起動（既存の実行パイプを流用）。
- 進捗・終了コードの扱いは既存 `main.js` の仕組み（PROGRESS_LINE 等）をそのまま使える。

## 9. CLI 仕様（案）

```
# 監視フォルダの登録・更新
uv run main.py monitor add <folder> --archive <archivefolder> --quota 50GB [--target 80%] \
    [--policy oldest_mtime] [--min-age-days 7]
uv run main.py monitor list
uv run main.py monitor disable <uid>

# スイープ（定期実行から呼ぶ本体）
uv run main.py sweep <folder|uid>            # 超過分を退避
uv run main.py sweep <folder|uid> --dry-run  # 退避予定を見るだけ

# 退避一覧（UI が JSON で読む）
uv run main.py evicted list <uid> [--batch <ts>] [--json]

# 復元
uv run main.py restore --ids 12,13,14
uv run main.py restore <uid> --prefix 旅行/     # フォルダ単位
```

- 終了コードは既存規約（0/1/2/3）を踏襲。退避 0 件でも失敗 0 なら 0。
- 既存サブコマンド（add/verify/…）とは**独立**。DB は同じ `dist/archive.db` を共有。

## 11. リスク・注意

- **atime が 3 OS とも不安定** → LRU は `max(atime, mtime)` に縮退させ、更新が止まっている
  環境は明示ログで警告（§5）。素の atime を鵜呑みにしない。
- **クロスプラットフォーム全般**（Win/Linux/mac）:
  - パス区切り・大文字小文字は既存の `to_posix`/`from_posix` と `lower()` 突き合わせを踏襲
    （DB は POSIX 相対で保持済み）。Windows の予約名/長パス（`\\?\`）は要確認。
  - 常駐/自動起動は OS ごとに実装差（login item / autostart .desktop）。
  - crawler が 3 OS で動くか未確認（§10-4）。動かない OS 用に内蔵ハッシュの検討。
- **アプリ内スケジューラはアプリ起動中のみ稼働** → 起動時スイープ＋任意のトレイ常駐で補う（§6）。
- **別ファイルシステムをまたぐ退避**は必ず copy→検証→削除（既存 safe_move で担保）。
- **監視ルートの移動/リネーム**: uid で追従（既存 Archive と同じ思想）。root_abs は更新。
- **同期フォルダ（iCloud/Dropbox 等）の監視**: オンデマンドDLの実体無しファイルを
  サイズ 0 と誤認しうる。将来 SharePoint 対応と同じ課題として別途検討。
- **無限復元⇔退避ループ**の防止（§7 の watermark と復元後保護）。
- **証拠で報告**（vault ルール）: スイープ結果は必ず「計測値・退避件数・解放バイト・失敗」を
  記録し、空振り（超過なしで 0 件）と失敗（測れなかった/移動できなかった）を区別する。
